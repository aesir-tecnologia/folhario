<threat_model>
T-02-17 unsigned-token acceptance: decoding without verification would let any caller spoof a user id. Mitigation: use `jose.jwtVerify` and never expose a decode-only success path.
T-02-18 proxy overreach: putting all authorization in Proxy can drift from route/use-case checks. Mitigation: Proxy fast rejects only obvious protected API misses; route helper verifies again.
T-02-19 JWKS local mismatch: Supabase JWKS can be empty with legacy signing keys. Mitigation: adapter fails closed with `unauthenticated` and the integration test prints a targeted message.
T-02-37 proxy body consumption: Next 16 proxies that read or stream the request body would render the downstream route unable to call `request.json()` or `request.formData()` (the stream is consumed once). Mitigation: proxy auth check looks ONLY at the `Authorization` header and URL; a UNIT test in this plan drives a `NextRequest` with a JSON body through the proxy and asserts the body stream is still readable post-proxy. The end-to-end version (real route handler in another wave parsing the body) is owned by Plan 09 because that is when the consent POST route exists.
T-02-38 ambiguous public allowlist: an unscoped string-match allowlist can drift (`/diagnostics/ping/extra` may pass a `startsWith` check). Mitigation: allowlist is a typed `RegExp[]` with anchored patterns (e.g. `/^\/api\/v1\/diagnostics\/ping$/`).
</threat_model>

Update `src/proxy.ts`:

1. Matcher includes `/api/v1/:path*` and still excludes `_next`, `_vercel`, and static assets.

2. Define a typed public-endpoint allowlist as anchored regex array (NOT substring match):
   ```ts
   const PUBLIC_API_ENDPOINTS: readonly RegExp[] = [
     /^\/api\/v1\/diagnostics\/ping$/,
     // Future public endpoints add here. Keep anchored.
   ] as const;

   function isPublicApiPath(pathname: string): boolean {
     return PUBLIC_API_ENDPOINTS.some((re) => re.test(pathname));
   }
   ```

3. For protected `/api/v1/*` requests (any path NOT matched by `isPublicApiPath`) without `Authorization: Bearer ...`, return `unauthenticated` 401 using the closed error response shape. Do NOT consume the body — `request.body` is never read; only the URL pathname and the `Authorization` header are inspected. For all other cases, call `NextResponse.next()`.

4. Do NOT verify JWT cryptographically inside Proxy; route helpers do that.

Create `tests/integration/auth-jwt.integration.test.ts` (existing test file — extend if present) that exercises adapter behavior for protected vs public paths and includes one test that uses `AuthAdapter` against a local JWKS endpoint.

Create `tests/integration/proxy-auth.integration.test.ts` (NEW file) that proves the public/protected status-code contract at the proxy boundary using ONLY routes that exist at wave 5. The only `/api/v1/*` route present at wave 5 is the existing public `GET /api/v1/diagnostics/ping`, so this test asserts:

a) `GET /api/v1/diagnostics/ping` (public) WITHOUT bearer returns 200 (proxy passes the request through to the existing ping route).

b) `GET /api/v1/some/non-existent-path` (or any not-yet-wired protected path under `/api/v1/`, e.g. `/api/v1/diagnostics/consent` whose route file does NOT exist yet) WITHOUT bearer returns 401 from the proxy. The assertion is on the 401 from the proxy, NOT a 404 from Next's router. Note inline in the test: this is a wave-5 contract test; end-to-end body-passthrough through a real protected route is asserted in Plan 09 because that wave introduces the consent route.

Do NOT issue requests in this file that depend on `/api/v1/diagnostics/consent` (Plan 09) or `/api/v1/photos/upload` (Plan 08); those routes do not yet exist when this plan runs.

Create `tests/unit/proxy-body-passthrough.test.ts` (NEW file) — a UNIT test that proves the proxy does not consume the request body, with NO dependency on any downstream route. The test:
- Imports the proxy function exported by `src/proxy.ts` directly (not via HTTP).
- Constructs a `NextRequest` (or a `Request` polyfill compatible with Next 16's proxy signature) with method `POST`, URL `https://example.test/api/v1/some-path-that-needs-bearer`, and a JSON body (`{ foo: 'bar' }`). Pass a valid `Authorization: Bearer <opaque>` header so the proxy is forced into the "passthrough" branch (cryptographic verification happens in route helpers, not in proxy).
- Calls the proxy function and captures the returned response (or `NextResponse.next()` payload).
- After the proxy returns, calls `await request.json()` (or reads `request.body` as a stream) and asserts the JSON parses successfully to `{ foo: 'bar' }`. If the proxy consumed the body, this read throws `"body already used"` and the test fails.
- A second, complementary case: pass NO `Authorization` header. The proxy should return a 401 response. After that response is captured, the test calls `await request.json()` again and asserts the body is still readable. (Even on rejection, the body stream must remain untouched — the route layer may want to log it elsewhere.)

If the Next 16 `NextRequest` API in scope makes "read body after proxy returns" awkward, an acceptable alternative is to spy on `request.body.getReader()` or assert that `request.bodyUsed === false` after the proxy returns. The point is the same: proxy does not consume the stream.
