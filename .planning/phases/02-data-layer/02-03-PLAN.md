<threat_model>
T-02-05 default-open data: tables created by raw SQL are accessible if RLS is not enabled. Mitigation: migration appends `alter table ... enable row level security` for every app table and a test fails if any table is missing RLS.
T-02-06 policy bypass by null auth: `auth.uid()` returns null for unauthenticated calls. Mitigation: policies include `(select auth.uid()) is not null`.
T-02-07 plain Postgres CI drift: CI service container may lack Supabase `auth` schema and roles. Mitigation: custom SQL creates a minimal `auth.uid()` helper and `authenticated` role only when absent.
T-02-29 silent RLS bypass via CI shim leaking to production: the conditional `auth.uid()` helper is intended for plain-Postgres CI only; if it ever loads in production it could either deny everything or, worse, allow everything depending on its return shape. Mitigation: `scripts/check-rls.ts` queries `pg_namespace` for `nspname = 'auth'` and throws a clearly worded error when `NODE_ENV === 'production'` AND the real Supabase `auth` schema is absent. Failure mode and runtime guard are documented in `02-10-SUMMARY.md`.
T-02-30 lost handwritten SQL on schema regeneration: appending RLS SQL to `drizzle-kit generate` output is brittle because regeneration overwrites it. Mitigation: handwritten SQL lives in its own `drizzle-kit generate --custom` migration file (`phase_02_rls_policies`) that schema regen never touches.
</threat_model>

Write the following handwritten SQL into that file. ALL idempotent guards (`IF NOT EXISTS`, `CREATE OR REPLACE`, `DO $$ ... $$`) are mandatory so the migration is safe against double-apply:

1. `CREATE EXTENSION IF NOT EXISTS pgcrypto;`
2. Conditional role creation:
   ```
   DO $$ BEGIN
     IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'authenticated') THEN
       CREATE ROLE authenticated;
     END IF;
   END $$;
   ```
3. Conditional minimal `auth.uid()` helper for plain Postgres / CI when Supabase's auth schema is absent:
   ```
   DO $$ BEGIN
     IF NOT EXISTS (SELECT 1 FROM pg_namespace WHERE nspname = 'auth') THEN
       CREATE SCHEMA auth;
       CREATE OR REPLACE FUNCTION auth.uid() RETURNS uuid
       LANGUAGE sql STABLE AS $fn$
         SELECT NULLIF(current_setting('request.jwt.claim.sub', true), '')::uuid
       $fn$;
     END IF;
   END $$;
   ```
   Add an SQL comment immediately above explaining: this helper exists for plain-Postgres CI only; production uses Supabase's real `auth.uid()`. `scripts/check-rls.ts` (Task 3) enforces the production guard.
4. `ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;` for every app table.
5. Reference-table authenticated read policies for `species`, `care_guides`, `identification_limits`, `provider_budgets`, `policy_versions`, and `partner_stores`. Wrap each in `IF NOT EXISTS` style by checking `pg_policies` first via `DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_policies WHERE policyname = '<name>') THEN ... END IF; END $$;`.
6. Owner `FOR ALL TO authenticated` policies for user-owned tables using `(select auth.uid()) is not null and (select auth.uid()) = user_id`. Same `IF NOT EXISTS` pattern as above.
7. Ownership indexes (`CREATE INDEX IF NOT EXISTS`) on `user_id`, `plant_id`, `species_id`, and `reminder_id` columns where policies or FK joins depend on them.
8. Conditional `auth.users -> public.users` insert trigger that runs only when `auth.users` exists. Wrap in `DO $$ BEGIN IF EXISTS (SELECT 1 FROM information_schema.tables WHERE table_schema = 'auth' AND table_name = 'users') THEN ... END IF; END $$;`. The trigger function inserts a `public.users` row with id = NEW.id, email = NEW.email, locale = `'pt-BR'`, timezone = `'America/Sao_Paulo'`, notification_time_local = `'09:00'`, created_at = `now()`. Above the function body, add a one-line SQL comment:
   ```
   -- Defaults timezone='America/Sao_Paulo' and notification_time_local='09:00' are first-row trade-offs only;
   -- Phase 4 signup will overwrite these from user input. Do NOT treat as policy.
   ```
   Use `ON CONFLICT (id) DO NOTHING` so re-running the trigger or replays do not error on the existing row from Phase 4 signup.

Do NOT seed business reference rows here; Plan 04 owns seed data.

After the file is written, run `pnpm db:migrate` to apply both migrations.
