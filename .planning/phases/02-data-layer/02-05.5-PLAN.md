<threat_model>
T-02-34 RLS-policy semantic drift: the conditional `auth.uid()` shim from Plan 03 lets migrations apply against plain Postgres in CI. The shim reads from `request.jwt.claim.sub` GUC. Real Supabase, however, wires `auth.uid()` to a JWT verified by PostgREST/GoTrue. If repositories run through a path where the GUC is unset OR where Supabase's real `auth.uid()` is not connected to our claims, owner policies silently degrade to "allow any" or "deny all" — both catastrophic. Mitigation: this plan's test connects through Supabase Auth's JWT-issuing path (real GoTrue) so the `auth.uid()` invoked by the RLS engine is the real one, and asserts cross-user denial behaviorally.
T-02-35 false-pass via misconfigured "deny all": a test that asserts only "user B cannot read row" passes if RLS denies everything (e.g. policy syntax error rejected by Postgres so all queries return zero rows). Mitigation: this test ALSO asserts user A CAN read its own row through the same path, anchoring the baseline.
</threat_model>

Setup phase (test-level `beforeAll`):
1. Construct two clients with `@supabase/supabase-js`:
   - `adminClient` using the service-role key. Used for `adminClient.auth.admin.createUser({ email, password, email_confirm: true })` to create two test users (user A, user B). On failure, throw with a clear message:
     `'Supabase Auth admin API is not reachable. Start local Supabase: supabase stop && supabase start. This test MUST NOT be skipped.'`
   - Two anon-key clients (one per user) and call `client.auth.signInWithPassword({ email, password })` to obtain JWTs. Store both `access_token` values.
2. The `auth.users` -> `public.users` trigger from Plan 03 will populate `public.users` rows on createUser. Verify both rows exist via the migration client; if not, throw with the explicit instruction to apply the migration (`pnpm db:migrate`).

Test cases (each MUST be a discrete `test(...)` block so test runners report individually):

a) BASELINE: user A inserts a `plants` row owned by user A through the application's UoW path:
   ```
   await withUnitOfWork(userA.id, async (tx) => {
     await tx.insert(plants).values({ id: plantId, userId: userA.id, name: 'Test plant A' });
   });
   ```
   Then, simulating a Supabase-faithful read path, the test creates a postgres-js connection that sets `request.jwt.claim.sub` to `userA.id` and queries `select * from plants where id = $1` (no explicit user_id filter — let RLS decide).
   ASSERT: exactly one row is returned. If zero rows are returned, the test fails with: `'Baseline read failed: user A cannot read their own row. RLS may be denying all reads — check policy and auth.uid() wiring.'`

b) DENIAL: using a separate connection with `request.jwt.claim.sub` set to `userB.id`, query the same `plants` row by id with NO explicit user_id filter.
   ASSERT: exactly zero rows are returned. If any rows are returned, the test fails with: `'CRITICAL: RLS did not deny cross-user read. plant id <id> owned by user A was visible to user B. Owner policies are not effective.'`

c) DENIAL VIA SUPABASE-CLIENT PATH: as a complementary check, attempt `userBSupabaseClient.from('plants').select('*').eq('id', plantId)` using the anon key + user B's access token (PostgREST path, the most Supabase-faithful surface).
   ASSERT: the returned data array has length 0. The test acknowledges this path verifies PostgREST's wiring of `auth.uid()`; the `request.jwt.claim.sub` path in (b) verifies the GUC-based wiring used by `withUnitOfWork`. Both must deny for the phase to be safe.

Cleanup phase (test-level `afterAll`):
- Delete the two `auth.users` rows via `adminClient.auth.admin.deleteUser(id)` and any leftover `plants` rows.

The test MUST NOT be conditionally skipped just because `SUPABASE_URL` looks like cloud — that path is already covered by the cloud-Supabase guard. The test MUST FAIL with the explicit message if local Supabase Auth is not reachable; do not introduce a `test.skip` for "auth admin returned 401" or similar, because skipping is the failure mode HIGH-1 calls out.
