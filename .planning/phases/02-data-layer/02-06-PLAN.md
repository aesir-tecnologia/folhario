<threat_model>
T-02-14 cursor tampering: malformed cursors can cause 500s or data leakage through unbounded queries. Mitigation: Zod-validated base64 JSON and closed `validation_failed` errors. Datetime validation enforces `offset: false` so non-UTC cursors are rejected, matching the PRD ISO-8601-with-Z constraint.
T-02-15 idempotency race: SELECT-then-INSERT can duplicate mutations. Mitigation: unique `(user_id,key)` row and transactional insert/lock semantics.
T-02-16 replay mismatch: same key with different body can return an unrelated response. Mitigation: NOT NULL `request_hash` (locked from Plan 03) and `conflict` for mismatches; tests cover both same-hash replay and different-hash conflict.
T-02-36 stuck idempotency on handler failure: if the handler throws inside `withIdempotency`, a non-transactional implementation might leave a partial idempotency row that blocks replay. Mitigation: the helper runs inside a transaction so a thrown handler rolls back the row and the next caller can re-execute. A test asserts handler-throws-then-replay re-invokes the handler.
</threat_model>

The `idempotency_keys.request_hash` column is NOT NULL (locked in Plan 03). The helper signature reflects this:

```ts
type WithIdempotencyInput = {
  userId: string;
  key: string;
  requestHash: string; // REQUIRED. Forbidden to omit. Compute as e.g. sha256(canonicalJson(body)).
};
async function withIdempotency<T>(
  db: DbClient,
  input: WithIdempotencyInput,
  handler: () => Promise<{ status: number; body: unknown }>
): Promise<{ status: number; body: unknown; replayed: boolean }>
```

RED: create integration tests asserting:
- FIRST CALL: `(userId, key, requestHash)` executes the handler, stores `response_status` and `response_body`, returns `replayed=false`.
- SECOND CALL with same `(userId, key, requestHash)`: returns the stored status/body without invoking the handler. Use a spy on `handler` and assert `handler` call count is 1 across both calls.
- HASH MISMATCH: `(userId, key, differentHash)` returns `ErrorCode.Conflict` (do NOT invoke handler, do NOT mutate the stored row). Assert handler call count is still 1 after this third call.
- HANDLER THROWS THEN REPLAY: a fresh `(userId, key2, hash2)` call where the handler throws an error. The transaction MUST roll back so no idempotency row persists. A subsequent call with the same `(userId, key2, hash2)` MUST execute the handler again (replayed=false on second call too) — assert handler call count for `key2` is 2 across the two calls. After the second (successful) call, the row is persisted and a third call returns `replayed=true`.
- TTL: rows have `expires_at = now() + interval '7 days'` (assert via DB query within ±5 seconds tolerance).

GREEN: implement `withIdempotency(db, input, handler)` using the `idempotency_keys` table inside a transaction. Strategy:
- BEGIN transaction.
- `INSERT INTO idempotency_keys (user_id, key, request_hash, expires_at) VALUES (...) ON CONFLICT (user_id, key) DO NOTHING RETURNING *`. If insert succeeded (returned row), this is a first call: continue.
- If insert returned no row (conflict): `SELECT * FROM idempotency_keys WHERE user_id=$1 AND key=$2 FOR UPDATE`. If `request_hash` differs from input, return `ErrorCode.Conflict`. Otherwise return the stored response (`replayed=true`).
- For first call: execute the handler. Update the freshly-inserted row with `response_status` and `response_body`. COMMIT. If the handler throws, the surrounding transaction rollback drops the freshly-inserted row, so a retry will be a fresh first call.

Do not implement SELECT-then-INSERT without `ON CONFLICT` handling.
