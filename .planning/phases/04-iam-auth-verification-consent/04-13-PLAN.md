<objective>
Close UAT Gaps 2 and 3 (POST /api/v1/iam/signup returns 500 in 3.1s for both organic and partner-code paths after the DB transaction commits — user is left with an account they cannot retry and never received a verification email).

Two-layer fix:

1. **Operational (immediate unblock for `pnpm dev` and any future `next start` runs without an Inngest event key):** force `INNGEST_DEV=1` in `pnpm dev` (mirrors `playwright.config.ts:77`) and document the variable in `.env.example`. The Inngest SDK then routes events to the local `inngest-cli dev` server (when running) or no-ops gracefully. No code-only fix can fully close the symptom without this — the SDK retries 5× before throwing.

2. **Architectural (prevents the user-trapping shape from ever returning):** decouple the email-dispatch fire from the signup write-path so a transient Inngest fault NEVER 500s a signup whose DB transaction has already committed. `inngest.send` calls in the signup, welcome-back, and resend-verification flows are wrapped in try/catch with `Sentry.captureException`. The bare `catch {}` blocks in the signup, resend-verification, and oauth-complete route handlers are replaced with `Sentry.captureException(err, { tags: { surface: ... } })` so future failures are surfaced to on-call instead of silently swallowed.

**Critical product impact (per UAT Gap 2 root_cause):** the signup DB tx commits BEFORE `inngest.send`. So when the user sees "500 Não foi possível concluir agora", their `auth.users` row, `consent_logs` rows, `subscriptions` row, and `email_verification_tokens` row have ALREADY been created. The user cannot retry (email is now taken) and never receives a verification email. The fix prevents this user-trapping outcome regardless of operational misconfiguration.

**Out of scope:** `password/reset-request/route.ts` already has an INTENTIONAL bare catch around `inngest.send` for D-11 anti-enumeration (sub-millisecond constant-time response, no signal whether enqueue succeeded). The existing comment at lines 61-65 documents this; do NOT touch this file. The other 7 bare-catch sites in IAM routes (`me/route.ts`, `me/password/route.ts`, `login/route.ts`, `password/reset/route.ts`, etc.) do not call `inngest.send` and are not in this gap closure scope.

Output: A `pnpm dev` signup that returns 200 in &lt;1s for both organic and partner-code paths; an architecturally-resilient signup that survives Inngest outages; route handlers that emit operator-actionable Sentry signals on genuine failures.
</objective>

<root_cause_recap>
From `.planning/debug/signup-route-500.md`:

`await inngest.send(...)` at `src/contexts/iam/application/signup.ts:139` throws because:
1. `pnpm dev` does NOT set `INNGEST_DEV=1` (only `playwright.config.ts:77` does).
2. The Inngest SDK's `mode` getter (Inngest.js:222-228) returns `"cloud"` when no `INNGEST_DEV` env, no `options.isDev`, no explicit dev URL.
3. `INNGEST_EVENT_KEY` in `.env:22` is the literal placeholder `"your-event-key"` — truthy, so `eventKeySet()` returns true (Inngest.js:270-272), bypassing the SDK's missing-key fast-fail.
4. SDK retries cloud delivery 5× with exponential backoff (100+200+400+800ms ≈ 1.5s sleep + 4-5 network attempts ≈ 3.1s total observed), then throws.
5. Thrown error propagates to `signup/route.ts:99-101` which has a bare `catch {}` swallowing the original error and emitting `errorResponse(ErrorCode.InternalError, "Não foi possível concluir agora.")` — the verbatim 500 the user sees.

**Why this is also a production-relevance bug, not a dev-only quirk:** the signup DB transaction commits BEFORE the `inngest.send` await. A transient Inngest outage in production with a real event key would 500 the signup AFTER the user record, consents, subscription, and verification token are persisted. The user is locked out (email is now registered) and gets no verification email. Operationally irrecoverable without manual intervention.
</root_cause_recap>
