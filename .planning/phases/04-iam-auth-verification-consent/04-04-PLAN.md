**auth_throttle cleanup:** D-12 has an OR clause: "Cleanup via Inngest cron (or partial index TTL)". Phase 4 chooses the partial-index TTL path — Plan 02 already added `auth_throttle_window_start_idx` which makes external sweeps fast. A real cron can be added in Phase 11+ if storage growth becomes a concern. NO `auth-throttle-cleanup` Inngest function in Phase 4.

**iam/password-reset-requested intermediate function (D-11 vs D-16 tension — surfaced as Decision Conflict to orchestrator):** D-11 mandates an `iam/password-reset-requested` Inngest function for anti-enumeration. D-16 + INFRA-10 limit the MVP to exactly 8 functions, none of which is this. To honor the orchestrator's "exactly 8" directive, Plan 08 will instead enqueue `notifications/email.requested` directly from the route handler AFTER an async user lookup, with the response returned immediately (the inngest.send happens before the response is built; the lookup happens inside an `await` block but the route still responds 200 unconditionally). This implementation honors D-11's "always-200" intent but diverges from its literal "emit `iam/password-reset-requested` event" wording. The Decision Conflict is surfaced for user resolution; the orchestrator prompt's directive ("reduce to exactly 8") takes precedence at planning time.
