Close UAT Gap 1 (cold-start AuthApiError surfaced as "Console AuthApiError: Invalid Refresh Token: Refresh Token Not Found" in the Next.js 16 dev overlay, attributed to PublicLayout). Two-layer fix:

1. **Structural (eliminates the recurring console.error):** add the standard `@supabase/ssr` Next.js middleware-level cookie-refresh step. Purpose: First-impression UX for Folhário. A scary red error in the dev overlay on the very first page load will scare off any developer/UAT volunteer trying to use the app, and tells production users (when this surfaces in Sentry) that something is broken when nothing is.

Output: Clean cold-start `/auth/login` render — no console errors, no recurring failed refresh attempts — for any user with a stale or absent Supabase auth cookie.

<root_cause_recap>
Two-layer cause from `.planning/debug/publiclayout-auth-refresh-token-throw.md`:

1. **PRIMARY (the visible error):** `@supabase/auth-js` 2.104.1 calls `console.error(refreshError)` at `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:3838` inside `_recoverAndRefresh()` whenever `supabase.auth.getUser()` (called from `getCurrentUserFromSessionReadOnly()` in PublicLayout) sees a stale cookie and the refresh attempt fails. The error is LOGGED, not thrown — Next.js 16's dev overlay attributes the SSR console output to the React owner stack (PublicLayout). `getUserBySession` correctly returns null; PublicLayout renders cleanly. The dev overlay is the only visible damage.

2. **COMPOUNDING (why it persists across renders):** `src/proxy.ts:96-119` does NOT implement the standard `@supabase/ssr` Next.js middleware-level cookie-refresh step. Server Components only see `getReadOnlySupabaseServerClient` whose Pitfall-6-mandated no-op `setAll` blocks `_removeSession()` (auth-js GoTrueClient.js:3841) from actually clearing the bad cookie. So the failed refresh + `console.error` recur on every Server Component render until the cookie is cleared client-side.

The structural fix is the missing middleware step. With it, the bad cookie is cleared before any Server Component runs, so auth-js never attempts the failed refresh during SSR.
</root_cause_recap>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser→middleware | Untrusted cookie attacker may send forged or stale `sb-*` cookies. Middleware createServerClient validates the cookie via Supabase Auth's JWKS / refresh endpoint. |
| middleware→server-components | Server Components see ONLY the cookie state AFTER middleware has run. Stale cookies are cleared upstream. |
