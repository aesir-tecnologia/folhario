<threat_model>
T-02-11 route-layer data bypass: importing Drizzle in handlers can skip use-case authorization and idempotency conventions. Mitigation: ESLint no-restricted-imports plus Vitest grep guard.
T-02-12 RLS-only authorization assumption: direct server SQL may not carry Supabase Auth context. Mitigation: repositories always accept `userId` filters and UnitOfWork sets DB request context only as defense in depth.
T-02-13 connection storm: Vercel warm invocations can open too many clients. Mitigation: lazy global singleton client.
T-02-32 GUC injection / wrong-shape userId: `set_config('request.jwt.claim.sub', userId, true)` accepts any string. A non-UUID value silently sets the GUC and any RLS policy comparing `auth.uid() = user_id` will produce confusing failures or, worse, accept a colliding value. Mitigation: Zod `z.string().uuid()` guard at the `withUnitOfWork(userId, fn)` entrypoint; non-UUID input throws `validation_failed` BEFORE the GUC is touched.
T-02-33 transaction-scope leakage: `set_config(..., true)` is `is_local = true` (transaction-scoped). If a developer accidentally calls a repository outside a UoW transaction, the helper currently has no defense and the GUC may be unset OR carried over from a previous call on a pooled connection. Mitigation: runtime assertion that the helper is operating inside an active transaction (Drizzle's `tx` callback signature; check the inner client is the transactional shape, not the singleton `db`); a unit test proves a repository called against `db` directly (not via `withUnitOfWork`) does NOT carry a leftover JWT claim from a prior UoW call.
</threat_model>

Create `src/shared/db/unit-of-work.ts` with this exact contract:

```ts
import { z } from 'zod';

const UserIdSchema = z.string().uuid();

export type DbClient = /* drizzle transactional client type, e.g. PgTransaction or PostgresJsTransaction */;

export async function withUnitOfWork<T>(
  userId: string,
  fn: (tx: DbClient) => Promise<T>
): Promise<T> {
  // 1. Validate userId at entry. Throws ZodError -> map to validation_failed at the route boundary.
  const validUserId = UserIdSchema.parse(userId);

  // 2. Open transaction. Drizzle's db.transaction(...) callback receives a tx client whose
  //    set_config(..., true) is transaction-local (is_local=true).
  return await db.transaction(async (tx) => {
    // 3. Runtime assertion: tx must be the transactional client shape, not the singleton.
    //    If the caller somehow bypassed db.transaction (e.g. mock plumbing), we throw before
    //    set_config writes a GUC that could leak.
    if (!isTransactionalClient(tx)) {
      throw new Error('withUnitOfWork: tx is not a transactional client');
    }
    await tx.execute(sql`SELECT set_config('request.jwt.claim.sub', ${validUserId}, true)`);
    return await fn(tx);
  });
}
```

`isTransactionalClient(tx)` is a small helper that checks for the Drizzle transactional shape (e.g. presence of the `rollback` method on the symbol/object Drizzle attaches inside `transaction()`). The exact predicate is the agent's discretion as long as: (a) it returns true ONLY inside a real `db.transaction(...)` callback, and (b) a unit test feeds the singleton `db` and asserts the helper throws.
