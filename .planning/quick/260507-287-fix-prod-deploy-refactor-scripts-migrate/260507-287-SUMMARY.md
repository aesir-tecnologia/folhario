# Quick Task 260507-287 — Summary

## Outcome

`scripts/migrate.ts` no longer transitively imports `src/shared/config/server-env.ts`. It reads `DATABASE_URL` via a local Zod schema and sets up its own postgres-js client. Production migration job in `.github/workflows/deploy-production.yml` (which only sets `DATABASE_URL` and `DATABASE_POOL_URL`) will no longer crash at module-import time on missing Supabase env keys.

## What changed

**File:** `scripts/migrate.ts` (+17 / -3)

- Removed: `import { closeMigrationSql, getMigrationSql } from "../src/shared/db/migration-client";`
- Added: `import postgres from "postgres";`, `import { z } from "zod";`
- Added: local `migrationEnv = z.object({ DATABASE_URL: z.string().url() }).parse(process.env)`
- Replaced helper calls with inline `postgres(migrationEnv.DATABASE_URL, { max: 1, idle_timeout: 5 })` and `sql.end({ timeout: 5 })` — options duplicated verbatim from `migration-client.ts`
- Updated docblock to call out the deliberate decoupling and reference T-02-02 (still: read only DATABASE_URL)

## What did NOT change (out of scope)

- `src/shared/db/migration-client.ts` — intentionally untouched. It's the documented T-02-02 mitigation surface (`.planning/phases/02-data-layer/02-SECURITY.md:44`) and is still consumed by `scripts/seed.ts`, `scripts/check-rls.ts`, `scripts/check-seeds.ts`, which run in environments with the full server env.
- `.github/workflows/deploy-production.yml` — kept `DATABASE_POOL_URL` set on the migration step. The line is now harmless dead env (the migrator never reads it). Removing it is a trivial follow-up cleanup if desired.

## Verification

- `pnpm tsc --noEmit` — passes (only an unrelated Node engine warning v24 vs `>=22 <23`)
- Module-load repro:
  ```bash
  env -i PATH="$PATH" HOME="$HOME" DATABASE_URL="postgres://stub" \

  ```
  Result: `IMPORT_OK` printed at module load (Zod parse no longer throws on missing Supabase keys); the script then runs `main()` and predictably fails the DNS lookup against `postgres://stub` — the runtime connection error is expected and unrelated to the import-time crash that was being fixed.
- `grep -nE "server-env|migration-client|serverEnv" scripts/migrate.ts` returns only the three documentation-comment lines that explain the decoupling — no actual imports remain.

## Reproducing the original failure (for posterity)

The failing CI step from run 25475882824 (`.github/workflows/deploy-production.yml:82-89`) sets only:

```yaml
env:
  DATABASE_URL: ${{ secrets.PROD_DATABASE_MIGRATION_URL }}
  DATABASE_POOL_URL: ${{ secrets.PROD_DATABASE_MIGRATION_URL }}
```

Before the fix, `pnpm db:migrate` → `tsx scripts/migrate.ts` → `import "../src/shared/db/migration-client"` → `import { serverEnv } from "@shared/config/server-env"` → `serverSchema.parse(process.env)` at `server-env.ts:42` threw:

```
ZodError: NEXT_PUBLIC_SUPABASE_URL invalid_type expected string received undefined
ZodError: SUPABASE_SERVICE_ROLE_KEY invalid_type expected string received undefined
```

After the fix, `scripts/migrate.ts` no longer reaches `server-env.ts`, so this Zod parse never runs.
