# Phase 02 Plan 05.5: Real-JWT RLS Cross-User Denial Proof Summary

**Single integration test (`tests/integration/rls-real-jwt.integration.test.ts`) that mints real Supabase Auth JWTs for two users via `auth.admin.createUser` + `signInWithPassword`, decodes the access_token to extract the `sub` claim, binds it inside a `SET LOCAL ROLE authenticated` transaction, and proves owner RLS policies deny cross-user reads with a baseline-anchored assertion that catches both silent "always-deny" misconfigurations and silent "always-allow" RLS bypasses. Closes HIGH-1 from `02-REVIEWS.md`.**

## Accomplishments

- **Real Supabase JWT path exercised end-to-end.** `auth.admin.createUser` against the local Supabase Auth admin API creates two users; `signInWithPassword` mints real JWTs; the test decodes each JWT and extracts the `sub` claim; that JWT-extracted sub is bound to `request.jwt.claim.sub` via `set_config(...)`. If any step in this chain diverges (createUser.id != JWT.sub, trigger doesn't fire, etc.), the test fails LOUDLY with the literal `MUST NOT be skipped` and an explicit remediation command.
- **Three test specs** (each as a separate `test(...)` block so failures report individually):
  1. **BASELINE** — userA reads their own plant through the RLS-protected query path. Returns exactly 1 row. Anchors the baseline so a misconfigured "deny all" RLS state cannot silently pass the denial spec.
  2. **DENIAL** — userB cannot read userA's plant through the same path. Returns exactly 0 rows. The CRITICAL failure message names both user ids and the plant id so a regression is immediately diagnosable.
  3. **auth.uid() probe** — Independent verification that `auth.uid()` resolves to the JWT-bound sub inside the authenticated-role transaction. Guards against a future regression where the policy is unchanged but `auth.uid()` returns null/wrong value. *(Replaces the plan's case (c) "Supabase-client / PostgREST path" which was omitted as a Rule 3 architectural exclusion — see Deviations.)*
- **Empirical sanity check passed.** Manually dropped `plants_owner_all`, re-ran the test, observed the BASELINE spec fail with the explicit "RLS may be denying all reads" message — proving the test is not a self-healing tautology. Restored the policy, re-ran, all 3 specs pass.
- **Cleanup is complete.** `afterAll` deletes both `public.users` rows (no FK cascade between auth.users and public.users) AND `auth.users` rows via admin API. Plant rows cascade out of public.users deletion. Verified no leftover `rls-userA-*` / `rls-userB-*` rows after a full run.

## Deviations from Plan

### Auto-added (Rule 3 — blocking issue)

**1. [Rule 3 - Blocker] `SET LOCAL ROLE authenticated` was missing from the plan's read query path**

- **Found during:** Test design (before authoring). Empirical psql verification ran the plan's exact prescribed shape (postgres-js connection, `set_config`, raw select with no user_id filter) and observed that the row was returned regardless of GUC value because postgres superuser bypasses RLS.
- **Issue:** Plan action describes "creates a postgres-js connection that sets `request.jwt.claim.sub` to `userA.id` and queries `select * from plants where id = $1` (no explicit user_id filter — let RLS decide)." But `DATABASE_POOL_URL` connects as `postgres` (BYPASSRLS=true) — RLS does not engage on superuser connections regardless of GUC. Without a role switch, the test would be a false-pass — the same silent-skip failure mode HIGH-1 calls out.
- **Fix:** Every read transaction in the test prefixes with `await tx.unsafe('SET LOCAL ROLE authenticated')` before binding the GUC. Verified empirically: with role switch + sub=userA, baseline returns 1 row; with role switch + sub=userB, denial returns 0 rows; without role switch, both queries return 1 row regardless of GUC.
- **Files modified:** `tests/integration/rls-real-jwt.integration.test.ts` (built into the test from the start, not retrofit).
- **Commit:** `62d7128`
- **Plan-text correction for future plans:** any test that "lets RLS decide" by skipping the user_id filter must run as the `authenticated` role, not as the connection's default role.

### Architectural exclusion (Rule 3 — out-of-scope path)

**2. [Rule 3 - Architectural] Plan case (c) "Supabase-client / PostgREST path" omitted**

- **Found during:** Pre-authoring environment check.
- **Issue:** Plan describes a third test case that uses `userBSupabaseClient.from('plants').select('*').eq('id', plantId)` against the anon key + user B's access token. This goes through PostgREST. The project's `supabase/config.toml` has `[api] enabled = false` per decision D-20 — the application never uses PostgREST; repositories use Drizzle inside `withUnitOfWork` directly. The local stack does not run a PostgREST container (verified: `supabase_rest_folhario` in the "Stopped services" list, port 54321 returns 503 for `/rest/v1/*` paths). Writing a test that depends on PostgREST against this stack would either fail with 503 (breaking CI for a test that proves nothing about this project's actual auth path) or have to silently skip when 503 — exactly HIGH-1's failure mode.
- **Fix:** Omit case (c) entirely. The `authenticated`-role + GUC path proves the same chain of custody (`Supabase JWT -> sub -> GUC -> auth.uid() -> owner policy`) and is what PostgREST itself relies on internally. Documented inline at the top of the test file with the rationale.
- **Files modified:** N/A — case (c) was never written.
- **Commit:** N/A — exclusion documented in test header + this SUMMARY.
- **Net effect on must_haves:** All four must_haves.truths still hold. The `auth.admin.createUser` and `signInWithPassword` literals are still present (in beforeAll); baseline + denial assertions are still present; loud-fail guard is still present.
- **Future-plan note:** If/when the project starts exposing PostgREST (e.g., for a Supabase-client-from-the-app pattern), a follow-up plan can add the PostgREST-path test. It is NOT a launch blocker because the application does not use PostgREST.

### Auto-added (Rule 2 — missing critical functionality)

**3. [Rule 2 - Critical] JWT-extracted sub used for GUC binding (chain-of-custody load-bearing)**

- **Found during:** Authoring (before first test run). The plan said "user A inserts a plants row owned by user A through the application's UoW path" and gave the GUC binding code as `set_config(..., userA.id, ...)`. That uses `user.id` from `createUser` rather than the JWT's `sub` claim.
- **Issue:** The plan's intent is to prove the chain `real Supabase issued a JWT -> JWT.sub -> GUC -> auth.uid() -> policy denies cross-user reads`. If the GUC is bound to `user.id` from `createUser` rather than the JWT's `sub`, the JWT becomes decorative — the test would still pass even if `signInWithPassword` returned a JWT with a different sub. That breaks chain-of-custody.
- **Fix:** The test decodes both access_tokens (`signInA.data.session.access_token`, `signInB.data.session.access_token`), extracts each `sub` via base64url JSON parsing, asserts that `JWT.sub === createUser.user.id` (loud throw if they diverge), and uses the JWT-extracted sub for `set_config`. If `signInWithPassword`'s implementation ever issued a sub different from createUser's id, the test fails immediately with the literal `JWT sub mismatch ... chain of custody is broken`.
- **Files modified:** `tests/integration/rls-real-jwt.integration.test.ts` (built in from the start).
- **Commit:** `62d7128`
