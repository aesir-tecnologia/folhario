## Phase 3 Inheritance

**This contract is scoped to Phase 4 net-new surfaces.** It does NOT redefine the design system — Phase 3 owns that. Every token, primitive, and rule below either:

1. References `docs/CAVE-PRD.md` §17 (Design System) as the canonical source, OR
2. References the Phase 3 ROADMAP entry (`Phase 3: Design System & App Shell`) and its 5 success criteria for primitives the executor inherits.

**Phase 4 inherits without redefinition** — when in doubt, defer to PRD §17:

- All color tokens (Paper Cream / Night Cream palettes, both light + dark variants) per §17 "Color tokens" tables
- Source Serif 4 + Plus Jakarta Sans typography per §17 "Typography" — variable fonts loaded by Phase 3
- Lucide icons (1.5px stroke, rounded line caps) per §17 "Iconography"
- 8pt grid + 4px exception for icon-to-label gaps per §17 "Layout > Whitespace"
- Global focus ring (3px Canopy Green @ 40% opacity, 2px offset, 8px radius) per §17 "Focus + keyboard"
- Skeletal shimmer loading (300ms threshold, 120ms fade-in, reduced-motion fallback) per §17 "Loading states"
- Spring-physics motion (120 stiffness / 18 damping / 1 mass; reduced-motion fallback) per §17 "Motion"
- Safe areas (`min-h-[100dvh]`, `env(safe-area-inset-*)`) per §17 "Safe areas + responsive"
- Bottom-nav (28px Lucide + label, 56px height + safe-area, 4 tabs) per §17 "Bottom navigation"
- All design system guardrails (no emoji, no pure black/white, no gradient text, no glassmorphism, no Inter, no generic serifs, no centered hero stacks) per §17 "Banned patterns"
- All accessibility rules per §18 (color never sole signal, redundant cues, image alt-text from context, decorative illustrations `accessibility hidden`)

**FLAG:** Phase 3 has not yet executed in this worktree. The planner must surface a hard prerequisite that Phase 4 cannot start until Phase 3 ships the design tokens, typography, focus ring, and bottom-nav primitives this contract assumes.

## Phase 4-Specific Interaction Contracts

These contracts define behavior the standard template doesn't surface. Each is a hard requirement for downstream verification.

### 1. Form input behavior contract (inherited from §17 "Inputs / forms")

All Phase 4 forms (signup, login, OAuth completion, forgot-password, reset, change-password) MUST:

1. **Validate on blur, never keystroke.** Zod schema runs on blur via the form library Phase 3 ships (or hand-rolled blur listener).
2. **Use semantic types + correct `autocomplete` tokens:**
   - Signup email: `type="email"` `autocomplete="email"` `inputMode="email"`
   - Signup new password: `type="password"` `autocomplete="new-password"`
   - Signup confirm password: `type="password"` `autocomplete="new-password"`
   - Login email: `type="email"` `autocomplete="email"` `inputMode="email"`
   - Login password: `type="password"` `autocomplete="current-password"`
   - Forgot password email: `type="email"` `autocomplete="email"` `inputMode="email"`
   - Reset new password: `type="password"` `autocomplete="new-password"`
   - Reset confirm password: `type="password"` `autocomplete="new-password"`
   - Change password — current: `type="password"` `autocomplete="current-password"`
   - Change password — new: `type="password"` `autocomplete="new-password"`
   - Partner code: `type="text"` `autocomplete="off"` `inputMode="text"` `pattern="[A-Za-z0-9-]+"`
3. **Error copy = CAUSE + RECOVERY** ("Senha precisa ter pelo menos 8 caracteres") — never color/icon alone (per §17 "Error states" + §18 "Color is never sole signal").
4. **On submit, auto-focus first invalid field + announce via `role="alert"` / `aria-live="polite"`.**
5. **Multi-error submit:** summary block above the form with anchor links to each per-field error, plus inline per-field errors.
6. **Forms >3 fields auto-save draft state locally.** Signup form has 5 fields (email, password, confirm-password, age-checkbox, T&C-checkbox) + optional partner-code → autosave to `localStorage` keyed `auth.signup.draft`. Drafts cleared on successful submit. Drafts NEVER include passwords (per §17 — passwords are always typed fresh).

### 2. Rate-limit (`rate_limited` 429) UX contract

When the per-IP throttle (D-12 / D-14: 5 attempts/minute, 5-minute lockout) trips on signup, login, OAuth callback, or password-reset-request:

- **Surface:** form-level summary block above the form (NOT toast, NOT modal, NOT full-screen).
- **Visuals:** Warm Ivory Surface card, 1.5px Overdue Rust stroke, 16px padding, filled `lucide:alert-circle` icon (Overdue Rust, 18px) left of headline.
- **Copy:** "Muitas tentativas. Tente novamente em alguns minutos." (verbatim — same on every endpoint).
- **No retry button.** Form remains submittable; user can wait + try again. No countdown timer (lockout is 5 minutes; surfacing the exact remaining time would invite scraping the throttle).
- **A11y:** `role="alert"` on the card; `aria-live="assertive"` on the headline so screen readers announce immediately.

### 3. Resend-verification cooldown UX (D-08, 1/min)

When the user taps "Reenviar e-mail" on the unverified blocker:

- **Optimistic state:** button immediately disables + label switches to "Enviando…" + shimmer on button background (300ms threshold per §17).
- **Success state:** label switches to "Aguarde 60s" with countdown decrementing per second. Button stays disabled. The countdown state IS the success affordance — no separate toast.
- **Countdown done:** button re-enables, label reverts to "Reenviar e-mail", `aria-live="polite"` announces "Você pode reenviar novamente."
- **Server-side cooldown trip (e.g. user has multiple tabs open):** server returns `rate_limited` 429; UI surfaces inline error per §2 above + recomputes the local cooldown to match server.
- **A11y:** every state change announced via `aria-live="polite"` on the button label; countdown updates throttled to once per second to avoid screen-reader spam.

### 4. OAuth-only conditional visibility (D-04 / AUTH-13)

In `/settings/account`, the change-password card is conditionally rendered based on `user.has_password`:

- **`has_password === true`** (email+password account): full change-password card with current-password + new-password + confirm-new-password fields + "Salvar nova senha" CTA.
- **`has_password === false`** (OAuth-only account, e.g. Google sign-in): change-password card REPLACED by a Calm Slate notice card with the locked copy: "Sua conta usa login com Google. Para alterar a senha, gerencie em sua conta Google." No interactive controls in this card.
- **Endpoint defense in depth:** `PATCH /api/v1/iam/me/password` rejects with `forbidden` 403 + body `{ error: { code: 'forbidden', message: 'Conta sem senha local.' } }` for OAuth-only users (UI prevents this; defense-in-depth per AUTH-13).

The `has_password` boolean is derived server-side from `auth.users.encrypted_password IS NOT NULL` (or Supabase's `user.identities` not containing only `provider: 'google'`); the IAM repository exposes it on the current-user resource.

### 5. Unverified blocker layout (AUTH-15, full-viewport takeover)

The blocker REPLACES the app shell when an authenticated user has `public.users.email_verified_at IS NULL` (per D-21 server-component check at root layout). It is rendered by the root layout's server component, not as a modal overlay.

## Discretion Decisions (within CONTEXT.md locks)

### Timezone picker UI in Settings → Account (CONTEXT.md "Claude's Discretion")

**Decision: simple text input with autocomplete suggestions** (NOT a dropdown of all 600+ IANA zones, NOT a timezone-by-region cascade).

- Field auto-detects from `Intl.DateTimeFormat().resolvedOptions().timeZone` on first render.
- User types to filter; suggestions render as a `<ul role="listbox">` below the input with up to 6 matches.
- Validation: server validates the submitted string is a real IANA zone (`Intl.supportedValuesOf('timeZone').includes(value)` per ECMA-402); invalid → `validation_failed` with copy "Fuso horário inválido. Tente algo como 'America/Sao_Paulo'."
- Brazilian zones surface first when typing common terms like "São Paulo", "Recife", "Manaus", "Fortaleza" — bias the suggestion ranking by `value.startsWith('America/')` and frequency among Brazilian users (Phase 4 hardcodes the 4 most common BR zones at the top of the suggestion list when the input is empty).

Rationale: dropdown of every IANA zone is overwhelming on mobile; a region cascade adds 3 taps for the 99% case where auto-detect is already correct. Phase 8 reminders depend on this being accurate, so we expose it but make it non-modal and forgiving.

### Additional paths in `UNVERIFIED_ALLOWED_PATHS` beyond AUTH-02's three categories (CONTEXT.md "Claude's Discretion")

Per D-23, the allowlist is default-deny + opt-in. Phase 4 adds these paths beyond the explicit list in D-23:

- `/_next/*` — Next.js static asset routes (already excluded by Next.js itself, but explicit for documentation)
- `/manifest.webmanifest` — PWA manifest (must be reachable while unverified or PWA install breaks)
- `/sw.js`, `/sw.js.map` — Serwist service worker (must be reachable for PWA chrome to render the blocker)
- `/icons/*`, `/favicon.ico`, `/apple-touch-icon.png` — favicons + PWA icons
- `/api/v1/diagnostics/*` — Phase 1 diagnostics routes (gated by `IDENTIFICATION_PROVIDER_MODE` env, not by user verification)
- `/api/inngest/*` — Inngest webhook receiver (signed by Inngest; no user JWT)
- `/api/v1/webhooks/stripe` — Stripe webhook receiver (Phase 10; signed by Stripe; no user JWT — already not in scope for Phase 4 but documented here for Phase 4's allowlist constant)

**Out of scope for the allowlist:** none of the catalog/identification/care-guide/reminder/billing endpoints are added; default-deny behavior holds for them per AUTH-02.

### Inngest cron schedule for `auth-throttle/cleanup` (CONTEXT.md "Claude's Discretion" / D-12 specifics)

**Decision: hourly cron at minute 17.** `cron: '17 * * * *'`. Deletes rows from `auth_throttle` where `window_start < floor((now() - INTERVAL '2 hours') / 60)` — i.e. retain 2 hours of buckets to cover any active 5-minute lockouts plus headroom for edge-case clock skew. Minute 17 chosen to spread cron load across the hour (not on the busy minute :00).
