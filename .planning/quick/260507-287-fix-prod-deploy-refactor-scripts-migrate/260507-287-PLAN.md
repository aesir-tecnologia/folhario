# Quick Task 260507-287 — Fix prod deploy: narrow migration env in scripts/migrate.ts

## Goal

Production migration step in `deploy-production.yml` fails because `serverSchema.parse(process.env)` at `server-env.ts:42` requires Supabase keys that the CI step deliberately does not provide. Refactor `scripts/migrate.ts` so it does not transitively pull in `server-env.ts`. Scope is intentionally narrow per the user's choice.

## Approach (chosen)

**Inline the postgres setup inside `scripts/migrate.ts`.** Read `DATABASE_URL` via a local Zod schema; do not import `migration-client.ts` (which imports `serverEnv`).

Rejected alternatives:
- *Refactor `migration-client.ts` to use a narrow schema:* broader scope than the user chose; touches a documented T-02-02 mitigation surface referenced in `.planning/phases/02-data-layer/02-SECURITY.md:44` and used by 3 other scripts (`seed.ts`, `check-rls.ts`, `check-seeds.ts`). Defer unless the user asks.
- *Add Supabase secrets to the workflow's migration env:* what option 1 was; the user picked option 2 specifically to avoid this.

## Tasks

### Task 1 — Inline narrow DATABASE_URL parse + postgres client in `scripts/migrate.ts`

**Files:** `scripts/migrate.ts`

**Action:**
- Remove `import { closeMigrationSql, getMigrationSql } from "../src/shared/db/migration-client";`
- Add `import postgres, { type Sql } from "postgres";` and `import { z } from "zod";`
- Add a local schema parsed at module load:
  ```ts
  const migrationEnv = z
    .object({ DATABASE_URL: z.string().url() })
    .parse(process.env);
  ```
- Replicate the connection setup from `migration-client.ts:17-22` inline (`max: 1`, `idle_timeout: 5`) and an inline close that mirrors `closeMigrationSql` (`sql.end({ timeout: 5 })`).
- Update the file's docblock: keep the existing rationale about why this script bypasses `drizzle-kit migrate`, and add a one-line note that it deliberately does NOT import `migration-client` because the helper transitively requires the full server env (Supabase keys) which production migrations do not have.

**Verify:**
- `pnpm tsc --noEmit` passes
- `grep -nE "server-env|migration-client|serverEnv" scripts/migrate.ts` returns nothing
- Repro the prod failure mode locally:
  ```bash
  env -i PATH="$PATH" HOME="$HOME" DATABASE_URL="postgres://stub" \
    pnpm exec tsx --env-file-if-exists=.env.local -e "import('./scripts/migrate').catch(e => { if (String(e).includes('NEXT_PUBLIC_SUPABASE_URL')) { console.error('REGRESSION'); process.exit(1) } else { console.log('module loaded ok (connection error against stub URL is expected and unrelated)'); } })"
  ```
  Module load must succeed without a ZodError naming `NEXT_PUBLIC_SUPABASE_URL` or `SUPABASE_SERVICE_ROLE_KEY`. (A subsequent connection error against `postgres://stub` is acceptable — the import-time crash is what's being fixed.)

**Done when:** `scripts/migrate.ts` runs `pnpm db:migrate` against a process env that contains only `DATABASE_URL` without throwing the Zod validation errors seen in run 25475882824.

## Out of scope

- `src/shared/db/migration-client.ts` — unchanged. Other consumers (`seed.ts`, `check-rls.ts`, `check-seeds.ts`) keep working and the documented T-02-02 mitigation line numbers stay stable.

Low. Single-file change. The only behavioral shift is removing an unintended import-time crash when Supabase env keys are absent. Connection semantics (`max: 1`, `idle_timeout: 5`, `sql.end({ timeout: 5 })`) are duplicated verbatim from `migration-client.ts`, so the migrator behaves identically once it actually connects.
