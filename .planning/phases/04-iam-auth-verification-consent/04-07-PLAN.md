<objective>
Implement email+password login and per-device logout. Login mints a Supabase session cookie via the AuthAdapter (Codex HIGH #3 — no server session table; per-device JWT semantics per D-05); logout calls `authAdapter.signOutLocal()` per resolved Q-AUTH-14, clearing the cookie + revoking the refresh token while leaving any existing JWT valid until its `exp` (≤1h on Supabase default).

Purpose: AUTH-05 (login per-device JWT) and AUTH-14 (logout this device). Resolved Q-AUTH-14 explicitly clarifies AUTH-14's wording: "clears the device's cookie and revokes its refresh token; the existing JWT continues to be valid until its `exp` (≤1h)". Plan 11 amends REQUIREMENTS.md AUTH-14 wording + ROADMAP.md Phase 4 SC-3 wording.

**Codex HIGH #3 fix:** Both use-cases consume the AuthAdapter from Plan 03; neither file calls `supabase.auth.*` directly.

**Codex HIGH #6 fix:** Replaces the prior plan's direct route-function tests for cookie/session flows with a Playwright E2E (`tests/e2e/auth-login-logout.spec.ts`). The E2E logs in via real HTTP, asserts the Supabase auth cookie is set, calls /logout, asserts the cookie is cleared (Set-Cookie with max-age=0 OR an immediate expiry), then attempts to use the refresh token via Supabase JS client and asserts it fails. Repository-level + use-case logic tests stay in vitest.

**D-31 fix:** Both routes are JSON-only — `request.json()`, never `request.formData()`.

Output: 2 route handlers + 2 application use-cases + 1 vitest integration test (login throttle + invalid_credentials behavior) + 1 Playwright E2E (cookie + refresh-token flow).

    // Phase 4 AUTH-05 + D-31 (JSON-only).
    import { NextResponse } from "next/server";
    import { errorResponse, ErrorCode } from "@shared/config/errors";
    import { withThrottle } from "@shared/api/throttle";
    import { loginRequestSchema } from "@contexts/iam/domain/schemas";
    import { loginUser } from "@contexts/iam/application/login";

    export async function POST(request: Request) {
      // D-15: increment ONLY on failure (successful logins don't consume the budget).
      // Codex HIGH #5: throttle middleware ALSO checks locked_until before counting.
      return withThrottle(request, "login", "on-failure", async () => {
        let body: unknown;
        try {
          body = await request.json();  // D-31: JSON only, NEVER formData
        } catch {
          return errorResponse(ErrorCode.ValidationFailed, "Corpo inválido.");
        }

        const parsed = loginRequestSchema.safeParse(body);
        if (!parsed.success) {
          return errorResponse(ErrorCode.ValidationFailed, "Validação falhou.");
        }

        const result = await loginUser(parsed.data);
        if (result.kind === "invalid_credentials") {
          return errorResponse(ErrorCode.InvalidCredentials, "E-mail ou senha incorretos.");
        }
        return NextResponse.json({ ok: true });
      });
    }
