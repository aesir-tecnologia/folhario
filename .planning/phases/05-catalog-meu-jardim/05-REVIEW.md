## Summary

Six files reviewed covering mutation hooks, i18n strings, a combobox primitive, sort preference persistence, service worker caching, and the journal server page. One critical finding: the journal page derives its `readOnly` flag from a non-existent environment variable (`SUBSCRIPTION_READ_ONLY`) instead of the documented cookie-gated pattern, so the prop it passes to `PhotoJournal` is always `false` regardless of subscription state — but `PhotoJournal` recovers via its own `useSubscription()` call, so UI gating still works in practice. The real danger is an undocumented, untested env path that masks the real mechanism and diverges from every other surface in the codebase. Four warnings cover: invalid HTML element IDs generated by the combobox for ghost rows containing spaces, stale option state in the combobox when the parent re-renders with new options, an unguarded `sessionStorage.setItem` write in the sort hook, and a misleading comment in the service worker. Two info items note duplicated serialization and a test-route-style escape hatch for a subscription gate.

## Critical Issues

### CR-01: `journal/page.tsx` reads undocumented `SUBSCRIPTION_READ_ONLY` env var — prop always `false`

**File:** `src/app/(app)/catalog/[plantId]/journal/page.tsx:38`
**Issue:** The page computes `readOnly` as `process.env.SUBSCRIPTION_READ_ONLY === "1"`. This env variable is defined nowhere else in the codebase (single grep hit, confirmed). The documented pattern for test-time read-only state is `ENABLE_TEST_ROUTES=1` + cookie `__test_subscription_read_only=1`, routed through `SubscriptionProvider` → `resolveSubscriptionState`. In both production and E2E test runs this env var is never set, so `readOnly` is always `false` when passed as a prop to `PhotoJournal`. The net effect is that `PhotoJournal` must rely entirely on its own `useSubscription()` client-side hook (line 47-48 of `photo-journal.tsx`), meaning the server-rendered initial state is always non-read-only. Should the server-side read-only determination ever matter (SSR, hydration safety, SEO snapshots), the gate is broken. Beyond runtime impact, this deviates from every other subscription gate in the codebase, is untested, and introduces a secret undocumented env knob.

**Fix:**

```tsx
// Remove the ad-hoc env read entirely. SubscriptionProvider already wraps
// the layout; photo-journal.tsx's useSubscription() is sufficient. If the
// server-side resolved value is needed, import the same resolver:
import { resolveSubscriptionState } from "@contexts/billing/application/subscription-provider";
import { cookies } from "next/headers";

// Inside JournalPage:
let cookieValue: string | undefined;
if (process.env.ENABLE_TEST_ROUTES === "1") {
  const cookieStore = await cookies();
  cookieValue = cookieStore.get("__test_subscription_read_only")?.value;
}
const { readOnly } = resolveSubscriptionState({
  enableTestRoutes: process.env.ENABLE_TEST_ROUTES,
  cookieValue,
});
```

Or, simpler: remove the `readOnly` prop from the `PhotoJournal` call and let it rely solely on `useSubscription()`, mirroring the approach on the plant profile page.

## Warnings

### WR-01: Combobox ghost row generates invalid HTML `id` when input contains spaces

**File:** `src/shared/ui/combobox.tsx:81` and `258`
**Issue:** The ghost row's value is built as `` `${GHOST_VALUE_PREFIX}${q}` `` where `q` is the raw user input (e.g., `"sala da TV"`). This value is then used verbatim as part of the element's `id` attribute at line 258: `` `${listboxId}-${opt.value}` ``. The HTML spec prohibits whitespace in `id` values. The same id is referenced via `aria-activedescendant` (line 207). Assistive technologies rely on `aria-activedescendant` pointing to a valid id; a malformed id causes AT focus tracking to silently fail when the ghost row is highlighted — an accessibility regression classified as a WCAG 2.1 failure (project marks A11Y as ship blocker).

**Fix:**

```ts
// In computeGhostRow, encode the query when building the value:
const safeQ = q.replace(/\s+/g, "_");
return { value: `${GHOST_VALUE_PREFIX}${safeQ}`, label: ghostLabel };

// commitOption already strips the prefix and returns the original typed text
// via onChange — the committed value is the raw label, not the id-safe value,
// so this change is safe. Alternatively use encodeURIComponent(q).
```

### WR-02: `filteredOptions` state not re-synced when `options` prop changes

**File:** `src/shared/ui/combobox.tsx:45`
**Issue:** `filteredOptions` is initialized from `options` at mount (`useState<ComboboxOption[]>(options)`), but there is no `useEffect` watching the `options` prop. If the parent re-renders with a different `options` array (e.g., `LocationCombobox` after the user commits a custom location and the parent adds it to the list), the combobox listbox shows the stale snapshot from mount time. The only reset path is `commitOption` (line 110: `setFilteredOptions(options)`) or `Escape` (line 173), both of which require user interaction. A user who opens the listbox after a parent-side update sees outdated options.

**Fix:**

```ts
// Add a useEffect to re-sync when options change:
useEffect(() => {
  setFilteredOptions(options);
}, [options]);
```

If the debounce timer is active when options update, clear it and recompute:

```ts
useEffect(() => {
  if (debounceRef.current !== null) {
    clearTimeout(debounceRef.current);
    debounceRef.current = null;
  }
  // Re-apply current query filter against updated options
  const filtered = query
    ? options.filter((o) => o.label.toLowerCase().includes(query.toLowerCase()))
    : options;
  setFilteredOptions(filtered);
}, [options]); // query intentionally omitted — only re-sync on source change
```

### WR-03: `setSort` in `use-sort-preference.ts` writes `sessionStorage` without try/catch

**File:** `src/app/(app)/catalog/_components/use-sort-preference.ts:34`
**Issue:** `readStoredSort` is fully guarded (`try/catch` around `sessionStorage.getItem`), but `setSort` calls `sessionStorage.setItem(STORAGE_KEY, next)` unguarded. In private/incognito mode, storage-disabled browsers, or when quota is exceeded, this throws a `DOMException` that propagates to the caller. The inconsistency between the defensive read and the unguarded write is a latent crash for a small but real user segment (private-mode browsing on iOS, for instance).

**Fix:**

```ts
function setSort(next: SortId): void {
  try {
    sessionStorage.setItem(STORAGE_KEY, next);
  } catch {
    // swallow — best-effort; sort reverts on next page load
  }
  setSortId(next);
}
```

### WR-04: Service worker comment contradicts implementation — `NetworkOnly` for `/api/*` is registered after `StaleWhileRevalidate` for catalog APIs

**File:** `src/app/sw.ts:36-37` and `87-109`
**Issue:** The block comment at lines 36-37 states "NetworkOnly for /api/*". In practice the `registerCapture` at line 87 installs `StaleWhileRevalidate` for `/api/v1/plants`, `/api/v1/photo-entries`, and `/api/v1/locations` before the `NetworkOnly` catch-all for `/api/*` at line 109. The comment inverts the actual precedence. A developer reading the comment to understand caching behavior will form the wrong mental model: they will believe all API routes use `NetworkOnly` and that catalog routes are special-cased to do so, when the opposite is true. This increases the chance of incorrect modifications to the runtime caching configuration.

**Fix:**

Update the comment block (lines 36-37) to accurately describe the layered strategy:

```
// - StaleWhileRevalidate for catalog GET APIs (/api/v1/plants, /api/v1/photo-entries,
//   /api/v1/locations) — registered first, takes precedence
// - NetworkOnly for all remaining /api/* routes — fallback for non-catalog APIs
```

### IN-02: `use-sort-preference.ts` uses `useEffect` for initial hydration — prefer lazy `useState` initializer

**File:** `src/app/(app)/catalog/_components/use-sort-preference.ts:24-31`
**Issue:** The hook initializes state to `"date_new"` and then immediately reads `sessionStorage` in a `useEffect` to set the real value. This causes a render-cycle gap: the component first renders with `"date_new"`, then re-renders with the stored value after mount. The eslint suppression comment (`// eslint-disable-line react-hooks/set-state-in-effect`) confirms this pattern is known to be non-idiomatic. `readStoredSort()` already guards against SSR via `typeof window === "undefined"`, so a lazy initializer is safe.

**Fix:**

```ts
export function useSortPreference(): [SortId, (next: SortId) => void] {
  const [sortId, setSortId] = useState<SortId>(readStoredSort);
  // No useEffect needed — readStoredSort() guards SSR via window check

  function setSort(next: SortId): void {
    try {
      sessionStorage.setItem(STORAGE_KEY, next);
    } catch { /* swallow */ }
    setSortId(next);
  }

  return [sortId, setSort];
}
```
